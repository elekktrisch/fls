# Epic 1 Context: The template — sign in, and see only your club

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

This epic is the template for the whole rebuild, not a feature in its own right. It fixes the id
strategy once, builds the repository skeleton and the client platform, and ships the nine build
gates with the CI that runs them, before any second slice exists. It also delivers the first real
capability: a user signs in through the identity provider, reaches only their own club's data, and
every change is audited. Every later epic copies a skeleton from here, so a shortcut taken now
repeats in every slice that follows.

## Stories

- Story 1.1: The build tree and the image
- Story 1.2: The runtime, the first migration, and the id strategy
- Story 1.3: The build gates and CI
- Story 1.4: The application shell and the design tokens
- Story 1.5: The record list and the list toolbar
- Story 1.6: See only your own club's aircraft
- Story 1.7: Sign in through the identity provider, and stay signed in
- Story 1.8: The person, the club membership, and the roles
- Story 1.9: The audit record
- Story 1.10: Edit my own record and my password
- Story 1.11: Reset a password, and confirm an email address
- Story 1.12: Manage the users of my club

## Requirements & Constraints

- A query without a club filter must return zero rows, never another club's data; a direct record
  identifier from another club must answer not found. A crew member or invoice recipient may belong
  to another club without exposing that club's other data.
- A user and a person are separate linked records. A person can exist with no user and can belong to
  several clubs, each with its own membership status and roles. A user belongs to exactly one club.
- Sign-in issues a short-lived access token that refreshes with no new sign-in during a flying day; a
  request rejected for an expired token must not lose unsaved entry.
- A role decides which surface and action a user reaches, and a permission failure names what is
  missing. A user edits their own person record and password, never their own role or club.
- A password-reset response is identical whether the email exists or not; a reset link expires after
  a fixed period and works once.
- Every create, update, or delete of a flight, person, aircraft, charging rule, or invoice draft
  writes an audit record (who, what, when, changed fields); a club reads only its own audit records.
- A club administrator manages only their own club's users: create, link to a person, assign or
  remove a role, deactivate; a deactivated user's audit records stay.
- Every list uses one as-you-type search field plus filter chips as the only filter mechanism, sort
  in the toolbar, no data table, and keeps row height when a value is absent.
- Navigation exposes exactly four destinations: Operate, Plan, Records, Admin.
- Also applies from this epic forward: no loading state under 300ms, no layout shift; no personal
  data in logs; Swiss/EU data residency; legibility (not full WCAG conformance) in the signed-in
  app, full WCAG 2.2 AA on public surfaces; dark-only display; errors reach the supplier with no
  database query; ASD-STE100 language in German and English; a latest-minus-one browser floor.

## Technical Decisions

- **Paradigm:** a modular monolith of vertical slices at two depths. A slice is thin (four files, no
  business rule) unless it has a state machine, a multi-record invariant, money, or exact legacy
  behaviour to reproduce — then it is deep (`domain/application/web/infra`, one dependency
  direction). This epic ships the reference pair: `core/aircraft` thin, `core/club` deep.
- **Repository skeleton (Structural Seed):** `server/platform`, `server/core`,
  `server/modules-open` (e.g. `flarm`), `server/modules-pro` (charging, invoicing, migration, ogn),
  `client/platform`, `client/features`, `deploy/`. `platform/` is the only cross-cutting dependency
  any slice may reach.
- **Module tiers:** core and open modules are Apache-2.0, both editions; pro is closed source, SaaS
  only. Core never references a pro module. CI builds and tests core + open modules standalone on
  every commit — that green build is the enforcement, not a repo split.
- **Id strategy:** UUID v7 for every table. Fixed 2026-08-30 by story 1.2. The PostgreSQL 18 native
  `uuidv7()` function is the column default; the matching Hibernate id generator mints the id via
  `uuidv7()` before the insert, so the row is written with a known id. No table diverges from this
  type.
- **Tenant isolation:** PostgreSQL row-level security plus `FORCE ROW LEVEL SECURITY` on every
  club-scoped table, generated by the same migration that creates the table. The app connects as a
  non-owner role; the club session variable is set exactly once, in the transaction opener, never in
  a controller, service, or query. One tenancy mechanism runs identically in a one-club community
  install and the SaaS. `club` itself is the tenant root, not a club-scoped table — its policy's
  `WITH CHECK (true)` is correct only because it carries no `club_id`. A real club-scoped table's
  policy must check the row's `club_id` against the session variable, never `true`.
- **Data kinds:** every table declares system reference (supplier-owned, read-only), club-scoped
  (RLS), or cross-club link (owning club creates it) — an undeclared table fails the build.
  `OwnerId`/`OwnershipType` never port; use a plain `club_id` foreign key.
- **Identity:** a small `IdentityProvider` port in `platform` (prove sign-in, create principal,
  deactivate principal, start password reset, start email confirmation). Keycloak is the reference
  adapter, realm imported from a repository file. Authorization never leaves the product: role, club
  membership, and tenant boundary live in AlpenFlight tables, resolved from `ClubMembership` on
  every request, never from a provider claim.
- **API and client typing:** REST, OpenAPI-published by the server; the client generates TypeScript
  from it and uses the generated type as the component's own type. A thin slice's client feature has
  no service layer — `httpResource` supplies value, loading, and error state.
- **Deployment:** one container image serves the API and built client; Docker Compose (image +
  PostgreSQL + Keycloak) is the supported install path for both editions; the node is stateless and
  disposable.
- **Stack:** Java 25 LTS, Spring Boot 4.1.1, PostgreSQL 18.6, Angular 22.0.1 (zoneless, stable Signal
  Forms/`resource`/`httpResource`). Gradle, Flyway, the OpenAPI generator, the IndexedDB wrapper, and
  Keycloak each need a version pinned and verified against release notes, not memory.
- **Nine build gates**, each with a CI proof-of-failure case, and each rule fails the build so no
  agent has to remember it: a thin slice has no `application/` package, a deep slice has all four;
  core never references a pro module; core plus the open modules build and test standalone; every
  club-scoped table has an RLS policy and every table declares its data kind; no binary
  floating-point type in a charging, delivery, or invoice type; no cross-slice reach into another
  slice's internals; a cross-tenant read test without a filter returns zero rows; no direct `now()`
  call, `Clock` is injected; every mutable entity carries a version column. Almost no real slice
  code exists yet, so most in-scope gates (1, 2, 3, 5, 6, 8, 9) run against production code that is
  still empty or near-empty for the rule in question; each one's checked-in, deliberately-violating
  fixture is the only proof today that the gate actually works, until real slices (starting with
  `core/aircraft` and `core/club`) and the first pro module give it real code to check.
- **Conventions:** naming from `domain-model.md`; no comment in hand-authored implementation code —
  a name and a structure carry the intent, so the code stays the one source of truth (exceptions:
  `package-info.java`'s Javadoc, and unmodified tool-scaffolded config like `tsconfig.json`); no
  markdown file restates a pinned version number — name the
  framework or tool only, the version lives once in the config that consumes it (exception: the
  spine's own Stack table, the ratified decision record); money as `BigDecimal`/`numeric`;
  dates/times store an explicit zone; soft delete is the default; a concurrent update returns a
  typed conflict via the version column; one error shape, translated to HTTP only in `web/`; German
  is the source language.
- **Testing:** `e2e/` is a read-only legacy oracle; AlpenFlight ships its own suite in `alpenflight/`.
  This epic's proof-of-life is a T3-equivalent smoke: sign in, read current user, read/write a
  flight, re-read to confirm persistence.

## UX & Interaction Patterns

- Dark-only, one token set (`DESIGN.md`): surface/ink/signal colours, monospaced tabular-numeral
  typography, a 4px spacing scale, zero corner radius (except the account portrait), 7:1 contrast
  floor, and short motion durations (110ms state change, 140ms reveal, instant for a press). No
  state is carried by colour alone — `AIRBORNE`, `LOCKED`, `UNSENT` each carry a word.
- `RecordList`/`RecordItem` is the one list component, no `<table>` element: stacked on a narrow
  viewport, aligned CSS-grid zones on a wide one; dense mode is pointer-only; an absent value keeps
  row height and reads `not set`; a grouped list shows a header naming the group and its count. List
  toolbar order is fixed: search field, then filter chips, then sort control.
- Four destinations (Operate, Plan, Records, Admin): bottom tab bar on a phone, top bar on a pointer
  device; every surface belongs to exactly one destination. Every focusable element keeps a visible
  focus ring; every input has a real label.

## Cross-Story Dependencies

- Stories 1.1 to 1.4 build the substrate in strict order: build tree/image, then runtime + id
  strategy + first migration, then CI build gates, then the application shell and tokens.
- Story 1.5 (record list and toolbar) needs the shell from story 1.4.
- Story 1.6 (club-scoped aircraft) needs the record list from story 1.5. The real `club` table and
  its one seeded row exist from story 1.2 on; story 1.6 reads that row's id from a temporary
  development source instead of a real sign-in.
- Story 1.7 (real sign-in) replaces and deletes that development source; a build test then fails if
  any code outside the transaction opener sets the club session variable.
- Story 1.9 (audit record) must ship before stories 1.10 and 1.12, because both write audit records.
- The id strategy fixed in story 1.2 gates every slice built after this epic.
- Open question 26 (a club for migrated legacy audit rows) blocks only the historical-data path;
  story 1.9 ships the new-record audit path regardless.
