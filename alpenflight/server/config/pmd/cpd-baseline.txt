# CPD duplication ratchet baseline — total duplicated tokens (J-5 T-11).
#
# The `cpdRatchet` task (build.gradle.kts) sums the `tokens` attribute across
# every <duplication> block in build/reports/cpd/cpdCheck.xml and FAILS the
# build iff that total exceeds the number below. So existing duplication debt
# passes; only NEW duplication reds CI.
#
# Lower is better. When duplication drops, cpdRatchet prints the new (lower)
# number — commit it here to lock the gain (the ratchet only tightens).
#
# Measured 2026-06-06 (J-5 T-11, PMD/CPD 7.25.0, minimumTokenCount=50, server
# main only): 5300 duplicated tokens across 65 clone blocks / 858 lines over
# 34,769 production LOC (~2.46% duplicated lines). The reservation aggregate
# (ch.alpenflight.reservations, T-03/T-09) is in only 9 small DTO/exception
# boilerplate clones — no logic duplication.
#
# Re-measured 2026-06-06 (J-6 T-02, PlanningDay aggregate seam): 5350 (+50). The
# `setInfo` free-text clone the PlanningDay aggregate would have shared with
# AircraftReservation was eliminated at source by extracting the shared-kernel
# `platform.text.FreeText.normalize` (both aggregates now delegate). The residual
# +50 is the one irreducible clone: the JPA id/@TenantId/info column-declaration
# block every tenant-scoped aggregate maps identically — abstracting it needs a
# @MappedSuperclass, which this codebase deliberately avoids (each aggregate maps
# its own tenant/audit columns, per the Flight/Aircraft/AircraftReservation
# precedent). Structural mapping boilerplate, not logic duplication.
#
# Re-measured 2026-06-06 (J-6 T-04b, planning REST resource T-04/T-05): the
# planning controller/service/mapper added NO logic duplication — its only CPD
# clones were the per-resource RFC-7807 advice boilerplate (the byte-identical
# problem(...) response builder + the generic 400 bad-request factory), the
# paged-envelope DTO record, and the JPA tenant column block. Rather than just
# absorb the +138, the genuine boilerplate was extracted at source: the new
# shared-kernel `platform.web.ProblemResponses` (problem + badRequest) now backs
# all 12 @RestControllerAdvice classes, collapsing the codebase-wide problem()/
# handleIllegalArgument() clone groups. Net effect: 5488 (red) → 4767, i.e. 583
# BELOW the prior 5350 baseline — the ratchet tightens. The 3 residual planning
# clones (53t handler scaffolding, 52t paged-DTO, 50t JPA column block) are
# irreducible: each Spring advice must own its @ExceptionHandler registration
# (no shared base class — same reason the JPA column block isn't a
# @MappedSuperclass), and the DTO/column shapes mirror reservations by design.
#
# Re-measured 2026-06-11 (J-7 RM-1b, flight-report read-model core): 4827
# (+60). The single new clone is the JPA column-declaration block
# (flight_aircraft_type_id/@Convert + flight_date + start/ldg_date_time)
# shared by the Flight write aggregate and the FlightReportRow read-model
# row. Pure field-declaration boilerplate, no logic: the read model
# deliberately mirrors the report oracle's columns (ADR 0027) and must stay
# mapping-independent from the write model so RM-3 can swap queries onto it
# — sharing the block via @MappedSuperclass/@Embeddable would couple the two
# models, the same abstraction this file already declines twice above.
#
# Re-measured 2026-06-11 (J-7 RM-2, rename-propagation events): 4883 (+56).
# The @DomainEvents emit-on-save methods added to Aircraft / Location /
# FlightType / Person were already collapsed to one-liners (the reducible
# part); the residual clone is that one-liner CHAINING with the byte-identical
# pre-existing softDelete(userId, clock) directly above it into one 56-token
# window across Aircraft/FlightType/Location. Spring Data requires
# @DomainEvents on each aggregate root, and the softDelete block is the
# already-baselined per-aggregate lifecycle boilerplate — extracting both
# would need the @MappedSuperclass this file declines three times above. A
# maintainability rider (_BOYSCOUT.md) tracks revisiting that stance now that
# five aggregates share the saved-event + soft-delete lifecycle shape.
#
# Re-measured 2026-06-13 (J-26 T-21, lifecycle @MappedSuperclass verdict
# EXECUTED): 4827 (-56). The recurring question this file re-opened three times
# above — extract a lifecycle base across the soft-delete + saved-event shape —
# is now DECIDED in ADR 0028, so the ratchet stops re-litigating it. The
# empirical clone was never "five aggregates": it was the 56-token triplet
# across Aircraft / FlightType / Location (Flight and Person have divergent
# softDelete signatures and never cloned). ADR 0028 splits the two halves: the
# boundary-clean soft-delete state + softDelete(userId, clock) + isDeleted() was
# EXTRACTED into the new @MappedSuperclass
# ch.alpenflight.platform.persistence.SoftDeletableAggregate (the three
# aggregates now extend it), collapsing the clone; the @DomainEvents
# emit-on-save hook STAYS per-aggregate (lifting it would couple the shared
# kernel to every module's *Saved event type — a Spring Modulith / ADR 0023
# boundary violation), and its ~15-token residual is below the 50-token CPD
# window. So the prior "this codebase deliberately avoids @MappedSuperclass"
# stance is superseded by ADR 0028's distinction: @MappedSuperclass for
# boundary-clean shared mapped state, NOT for module-coupled behavior.
#
# Re-measured 2026-06-13 (J-8 T-07, accounting reference-data endpoints): 5009
